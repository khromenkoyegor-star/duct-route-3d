# CLAUDE.md — Траса 3D (робоча назва)

## Що ми будуємо
Веб-додаток (PWA) для фахівця з промислової вентиляції.
Користувач сканує приміщення в Polycam, експортує скан у GLTF/GLB, відкриває його в додатку і малює в скані трасу повітропроводу — полілінію, яка є **центральною віссю** труби. Потім додаток будує з траси 3D-модель повітропроводу з оцинкованої сталі заданого діаметра. Пізніше — розрахунок площі поверхні деталей для кошторису й деталювання.

Етапи та їхній статус — у `ROADMAP.md`. Це головний план, працюй строго по ньому.

## Хто користувач
- Єгор — практик промислової вентиляції, не програміст. Пиши йому **українською**, простими словами, без жаргону. Коротко: що зроблено, що перевірити, що далі.
- У нього **немає комп'ютера** — тільки iPad і iPhone. Ніколи не проси його запустити команду в терміналі чи щось встановити. Усе, що він має побачити, має відкриватися за посиланням у Safari (GitHub Pages).
- Розміри стандартних повітропроводів і фасонних деталей дає **тільки Єгор**. Не вигадуй їх. Поки їх немає — тимчасові значення, явно позначені в коді коментарем `// TEMP`.

## Цільові пристрої
- iPad, Safari, горизонтальна орієнтація. Основне керування — мишка з курсором; дотик теж має працювати.
- iPhone 15 Pro Max, Safari, дотик (вертикально й горизонтально).
- Додаток додається «На початковий екран» і відкривається на весь екран (PWA: manifest, іконки, `display: standalone`).

## Стек
- Vite + TypeScript (strict) + Three.js.
- Three.js addons: `GLTFLoader`, `OrbitControls`, `TransformControls` (гізмо зі стрілками).
- Інтерфейс — звичайний HTML/CSS поверх canvas. Нову бібліотеку додавай лише тоді, коли без неї ніяк, і поясни чому.
- Тести: Vitest (ядро), Playwright (сценарії в браузері + скріншоти).
- Публікація: GitHub Actions → GitHub Pages після кожного злиття в `main`. Репозиторій публічний.

## Структура коду
- `src/core/` — чиста логіка: вузли, сегменти, повороти, деталі, площі, одиниці. **Без Three.js і без DOM.** Усе тут покрито тестами Vitest.
- `src/scene/` — Three.js: завантаження скану, камера, гізмо, побудова мешів із даних `core`.
- `src/ui/` — панелі, кнопки, поля вводу.
- `tests/unit/`, `tests/e2e/`, `tests/fixtures/` — синтетичні сцени з відомими розмірами (наприклад, кімната 4000 × 2700 × 3000 мм).

## Координати й одиниці — не порушувати
- Вертикальна вісь — **Y** (вгору = +Y). Горизонтальна площина — **XZ**. Це стандарт glTF і Three.js: нічого не перераховуємо й не обертаємо.
- Сцена в **метрах** (як glTF). Інтерфейс показує й приймає **міліметри**. Переведення м ↔ мм — тільки в `src/core/units.ts`.
- Масштаб завантаженого скану ніколи не змінювати: 1 одиниця сцени = 1 м реального простору.

## Модель даних
- Траса = впорядкований список вузлів (координати в мм) + параметри (діаметр, матеріал).
- Лінія траси — це вісь (центр) повітропроводу.
- 3D-геометрія завжди генерується з даних траси, ніколи навпаки. Дані — єдине джерело правди: з них потім рахуємо площу, специфікацію й кошторис.
- Правила версії 1: у горизонтальній площині — прямо або поворот вліво/вправо на 90° чи 45°; вертикально — лише строго вгору/вниз по Y.

## Інтерфейс
- Відчуття нативного iOS/iPadOS: системний шрифт (`-apple-system`), панелі в стилі iPadOS, світла й темна тема.
- Кнопки й поля не менші за 44 × 44 px. Нічого, що працює тільки при наведенні курсору.
- Pointer Events (мишка, дотик, курсор iPadOS); враховуй safe areas.
- Камеру можна вільно обертати в будь-який момент, навіть коли точка редагується (вимикати орбіту лише на час перетягування стрілки гізмо).
- Короткий клік ставить/вибирає точку, перетягування — обертає камеру. Ці дії не мають конфліктувати.

## Скани й приватність
- Скани відкриваються локально на пристрої і **нікуди не завантажуються** — ні на сервер, ні в репозиторій.
- На iOS фільтр `accept` у полі вибору файлу може зробити .glb/.gltf неактивними — не обмежуй вибір жорстко, перевіряй тип файлу після вибору.
- Скани Polycam бувають важкими, а пам'ять Safari на iPhone обмежена: звільняй геометрії й текстури (`dispose`), показуй розмір скану й кількість трикутників, попереджай, якщо скан завеликий.

## Як працюємо
1. Беремо наступний незакритий етап з `ROADMAP.md`. Один етап за раз.
2. Спочатку план (режим планування): що робимо, які файли, як перевіримо. Короткий і зрозумілий Єгору. Чекаємо його «так».
3. Реалізація малими кроками з комітами.
4. Перед здачею: `npm run build`, `npm test`, `npm run test:e2e` — усе зелене.
5. Делегуй перевірку субагентам: `tester` (функції й геометрія за «Критеріями готовності» етапу) і `ux-reviewer` (інтерфейс на iPad і iPhone). Виправ усе, що вони знайшли, і перевір ще раз.
6. Онови `ROADMAP.md` (статус, нотатки) і відкрий PR. Опис PR — українською: що змінилось і покроково, що Єгору перевірити на iPad/iPhone.

## Заборони
- Не починати етап «Фасонні деталі», поки Єгор не дав приклад вузла й розміри. Коли дійдемо до цього етапу — першим повідомленням нагадай йому про це.
- Не вигадувати стандартні розміри повітропроводів і фасонних деталей.
- Не змінювати масштаб і осі скану.
- Не розширювати обсяг етапу без погодження — нові ідеї записуй у розділ «Ідеї на потім» у `ROADMAP.md`.

## Команди (з'являться на етапі 0)
- `npm run dev` — локальний сервер
- `npm run build` — збірка
- `npm test` — тести ядра (Vitest)
- `npm run test:e2e` — сценарії й скріншоти (Playwright; профілі «iPad landscape» і «iPhone 15 Pro Max»)
